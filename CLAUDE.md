# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Chronicles is a **zero-knowledge encrypted journal application** rebuilt as a **React + Express monorepo** (no Next.js) for React Native readiness. The server never sees plaintext user data.

Key privacy guarantees:
- All entry content encrypted client-side with AES-256-GCM before transmission
- Non-extractable CryptoKeys — master key cannot be exported from the browser's crypto subsystem
- Split-token sessions — database leaks cannot reconstruct valid tokens
- Recovery key provided at registration for password recovery

## UI Design Rules

The design system lives **in the app code** (the separate `design-system/` folder was folded in):
- **Tokens** — `client/src/App.tsx` (`STATIC_CSS_VARS`, `LIGHT_CSS_VARS`, `DARK_CSS_VARS`, accent
  derivation): the semantic CSS variables below are the source of truth for colour, type and radii.
- **Core primitives** — `client/src/components/atoms/core/` (`Icon`, `Input`, `Textarea`, `Select`,
  `Checkbox`, `Button`, `Badge`; `.jsx` + `.d.ts`) styled by the `ch-*` classes in
  `client/src/styles/core.css`. App code uses the atom wrappers (`TextInput`, `Select`, …) and
  `Icon` from `atoms/core/Icon.jsx`.
- **Shared patterns** — field rows `FormField` + `styles/filledInputs.ts`, `PillButton`,
  `CollapsibleCard` (lifted panel: `--bg-surface` fill + `--border-subtle` hairline; an `outlined`
  variant — no fill, a brighter `--border-default` outline — exists but is unused),
  **column borders on spreadsheet tables** (not the entry lists — journal/topic/health lists have
  none) — `columnRules(padY)` for grid rows (finance `Row`/`TotalRow`) and `tableColumnRules` for
  `<table>`s (Meals, print report)
  (`styles/columnRules.ts`); new table-like layouts use them too. Rules must run unbroken
  top to bottom, so: finance tables pass their columns to `Table` (`$cols`, `$phoneCols`,
  `$phoneAt`) and rows/headers/totals share them by subgrid (totals live *inside* the
  `Table`, spaced with cell padding, never a margin); a cell that wraps onto its own line on
  phones repaints the rules with `continueRules(columnsToTheRight - rowPaddingRight)`,
  `EntryListCard`/`EntryTable`, and for reports `StatTile`/`StatTileRow` (a `--bg-panel` card: name top-left, muted
  caption top-right, 56px thin Work Sans figure + unit, 4px rule in the metric's colour; the chosen
  one gets a light grey `--border-default` outline) and `charts/TrendChart` (faint grid over a firmer baseline,
  0 / half / max ticks, main line + dots in its `--chart-*` colour, dashed grey ghost lines; its
  legend is `ChartLegend`, placed in the card's title row). Reuse these rather than restyling locally.
All UI must follow the rules below.

### Design Philosophy
- **Borderless tonal panels** — Soft grey canvas `#f4f5f7` with near-white `#fbfbfc` cards (light) / slate `#1f2229` with bright, high-contrast
  greys (dark) — keep dark-theme greys bright; users find mid-greys washed out.
  Cards and inputs separate from the canvas by **fill tone**, not outline. Visible borders are
  hairline dividers only. **Inputs are filled** (`--bg-sunken`), not outlined.
- **Dashboard widgets sit in grey cards**: on the home dashboard every section in the two columns
  (priorities, coming up, quick meal log, exercise, recent entries, shopping, menu, medications, log a symptom) is
  in its own `--bg-panel` card (14px corners, 28px / 32px padding, `WidgetCard` in `DashboardView`)
  like Next up, the daily quote and the world clocks — a title in the dashboards' **card label** (`cardLabel` in `styles/cardLabel.ts`: 12px Open Sans 600, 0.12em tracked capitals, `--text-muted` — shared by every home / Health dashboard card title, the Quick entry, Daily quote and World clocks labels) over a light `--border-subtle` rule inside, 16px above the content, a grip just left of the chevron that drags the card (dnd-kit, the grip only — within a column or across to the other; the order is saved as `dashboardConfig.layout` `{ left, right }`, cards it doesn't know go back to their default column, `fullLayout`), and a chevron at the top right that folds the card down to its title row (a folded card has no fill or outline — just its title row, edge to edge across the column) (a picker card — Shopping list, Tasks — folds to just its title, hiding the picker and +, so it never looks like an empty list) (on phones, ≤768px, every card starts folded — the ones opened there are `dashboardConfig.openOnPhone`, separate from the wider screens' `collapsed`) (the title row is the chevron's 30px tall with its link centred, so they line up; widget heads carry no counts — no "2 of 10 done" / "3 left") (saved in `dashboardConfig.collapsed`). The grid
  is `1fr / 1fr` with 24px gaps between cards and columns.
- **Softly squared corners** — Cards/tiles and styled-form boxes 6px (`--r-lg`), filled inputs ~1px (`--r-md`). Action
  buttons are the round `PillButton` (`--r-full`); small utility controls (search fields, Clear,
  bulk-edit buttons) use a slight 4px radius. Avatars, switches and dots are round.
- **Flat elevation** — Depth is tonal layering, **never shadow** on resting panels. Shadows
  (`--shadow-lg/xl`) are reserved for floating overlays: dropdown menus, dialogs, toasts.
- **One confident accent** — A single user-selectable accent marks exactly one active/selected
  thing (a solid accent block, or a 2px accent left-bar + faint accent tint). Never decorative.
  A **chosen filter pill** is a **solid accent fill with `--on-accent` text** (Cycle chips, Planning's Goal / Milestone / Status filter pills and action pills like Re-estimate are outline pills instead: accent outline (`--color-accent-line`) + accent text (`--color-accent-soft`), no fill) —
  never a see-through accent tint with accent text. `--on-accent` is white unless the fill shown
  is too light for it (< 2:1 — yellows, pastels), then
  near-black (`onAccentFor` in `App.tsx`); all 30 presets keep white.
  A 3px accent stripe pins the very top of the app chrome.
- **Type** — **Work Sans** for display/headings, set **thin (Light/200–300)** for an airy feel;
  **Open Sans** for UI, body, and metadata (uppercase + `~0.14em` tracking). Sentence case in UI.
  Both are **bundled with the app** (`client/src/styles/fonts.css` + `src/assets/fonts/`) — never
  load them from Google Fonts, which Safari/iOS can block, leaving a system face. **One static file
  per weight and style**, never a single variable-weight file (iOS doesn't render those reliably):
  Work Sans 100–700, Open Sans 300–700, normal + italic, latin + latin-ext. A new weight needs its
  own files and `@font-face` rules (Fontsource packages have them). The **Material Symbols** icon font is bundled
  too (a subset of the glyphs listed in `src/assets/fonts/material-symbols-icons.txt`, fetched by `npm run fonts:icons`, which also stamps its url in `fonts.css` with `?v=<hash>` so a browser holding the old subset loads the new one),
  so no page load calls Google — the CSP allows no font or style hosts beyond `'self'`. **Icon weight**: set `font-weight` to the same value as the `'wght'` in `font-variation-settings` (`MaterialIcon` is 300; the mood faces 100) — Safari on iPad / iOS draws the variable icon font at the CSS weight and can ignore the variation setting, which made the faces bold there.

### Two Themes: Light (white) and Dark (charcoal)
Switched via `data-theme="dark"` on `<html>` (driven by `uiStore.themeMode`, the theme in effect — set by the Light / Dark / Auto choice). The token layer
is injected in `client/src/App.tsx`. DS semantic tokens (use these for new work):
- `--bg-app`, `--bg-surface`, `--bg-sunken`, `--bg-hover`, `--bg-active` — surface layers
- `--text-primary`, `--text-secondary`, `--text-tertiary`, `--text-disabled` — text tones
- `--border-subtle`, `--border-default`, `--border-strong` — hairline borders
- `--border-card` (card outlines and their inner rules/boxes), `--text-muted` (card subtitles, chevrons, + icons), `--text-placeholder`, `--control-border` (unticked round checks), `--bg-row-hover` (a row lifting inside a card, #2f313a), `--text-soft` (toolbar text buttons, #a5a8b0), `--text-faint` (quiet + marks, #464a54), `--bg-tile` (filled tiles, #2c2e37), `--bg-today-col` (today's column band, #262831), `--color-accent-link` / `--color-accent-soft` (lighter accent text in dark: links / today's label), `--border-pop` (floating menus, #373a44), `--border-dashed` (#3b3f49), `--text-hint` (placeholders in big borderless fields, #60636c) — sampled from the card mockup (dark #31343d / #7c7f88 / #6c6f78 / #5b5f69)
- `--color-accent`, `--color-accent-hover`, `--color-accent-subtle`, `--on-accent`,
  `--accent-100..800` — accent scale derived programmatically from the user's hex
- `--font-display` (Work Sans), `--font-sans` / `--font-label` (Open Sans)

**Legacy aliases** (`--paper*`, `--ink*`, `--rule*`, `--btn-primary*`, `--accent-fill*`, `--mono`)
still resolve, remapped to DS values in `App.tsx`, so existing components recolor automatically.
Prefer the DS-named tokens in new/edited code.

### Light theme — weight and contrast
Light needs much darker text than dark needs light text, so it's tuned separately (`LIGHT_CSS_VARS` + `html[data-theme='light'] &` rules):
- **Soft light, not white**: page `--bg-app` #f4f5f7, cards `--bg-panel` / `--bg-surface` #fbfbfc, controls (pills, chips, the topic picker — `--bg-control`) **transparent: no pill or chip is ever filled** (the floating timer, welcome tour and view menu keep their own solid #fefefe / #fff surfaces), the wellness four-square card `--bg-tracker` #fbfbfc, journal list + rail `--bg-sunken` / `--bg-rail` #dcdfe4 (logo cell #d3d7dd, active item #f4f5f7), chosen toggles `--bg-active` #d3d7dd, chosen pills an accent outline and text only — `--bg-selected` is no longer set (no tinted fill in either theme)
- Near-black text (`--text-primary`/`--text-secondary` #1f2128, 13:1), card labels / toolbar text `--text-soft` #4a505b (6.7:1), secondary text, units and placeholders (`--text-muted`/`--text-meta`/`--text-placeholder` #575d68, 5.5:1), card/input outlines #cdd1d8 (`--border-card`, `--border-field`), dividers `--border-default` #bfc4cc, row hairlines `--border-subtle` #d3d7dd, the lightest hairline `--border-faint` #e6e8ec (the topic picker's menu, the lines between Medications / Exercise schedule rows; = `--border-subtle` in dark)
- Pills and round controls (neutral `PillButton`, field chips, Cycle chips, the quick-entry topic pill, dashboard shopping pills) and unticked checks (`--control-border`) outline in #80868f (3:1) — the light-only `--border-pill` token, unset in dark (`''` in `DARK_CSS_VARS`) so each control keeps its own dark outline; `--progress-track` (#d3d7dd), `--bg-control` and `--bg-tracker` work the same way
- One clear structure: the journal list (`--bg-sunken`) and the rail (`--bg-rail`) share #dcdfe4, a step darker than the #f4f5f7 page
- A deeper accent for text and outlines on white: `--color-accent-line` (outlined accent pills, chosen chips/segments, Save), `--color-accent-link` / `-soft` / `-text` and the active nav item (`--color-accent-nav`) are the accent × 0.68 in light (Teal → ~#23706e, 5.2–5.9:1); progress-rule fills use `--color-accent-fill` (× 0.84 in light, Teal → ~#2c8b88); `--color-accent` itself stays the exact accent (other fills, logo). In dark `--color-accent-line` / `-fill` / `-nav` = the accent
- **Save entry** in the journal's tool row is filled in `--color-accent` with dark text (#15181d) in both themes — the strongest thing at the foot (a quiet grey outline while there's nothing to save); the Quick entry's stays an accent outline
- No small tracked capitals in light: `PillButton`, `FormField` labels, the journal list's topic label, `NutritionPanel` labels and the save-status notes switch to sentence case at normal spacing (13–14px, 500) — dark keeps the tracked caps
- Big titles stay thin; body text and values are 400–500 in near-black

### Accent customization
Settings → Theme offers **30 named accent presets** (`ACCENT_PRESETS` in `SettingsView`, ordered by hue: reds, oranges/yellows, greens, blues, purples, neutrals — all toned to the same muted chroma). Any hex feeds `--color-accent` and
`deriveAccentScale()` builds the `--accent-100..800` ramp. `--color-accent` is the user's **exact** colour in both themes — no dark-mode lift (only hover/pressed step lighter in dark). The nav rail's active item is the exact accent in dark and the deeper × 0.68 text accent in light.

### Component-specific Rules
- **List rows — one style everywhere** (`styles/entryRow.ts`, used by `EntryCard`, `EntryListCard` and the Topics list): journal (`entryRow`): rows have no background of their own; hover/focus shows only a 4px accent left bar (the background never changes on hover); the open entry on `--bg-app` (the editor's colour) with the bar — the list pane itself is a shade darker (`--list-bg`, set on `JournalTemplate`'s side panel: `--bg-app` 80% toward black in dark, 95% in light) so it reads as a drawer beside the editor, with no divider between them — and the topic + date are never accent — on every list they recede in `--text-meta` grey (hover and the open row included); every other list (`entryRowPlain` — topic pages, Topics, Health lists, Recipes, Shopping, Planning lists, dashboard lists) — rows on `--bg-app`, and hover / the active row draw a rounded accent (`--color-accent-line`) outline (10px corners, 14px wider than the row each side, since the text is flush with the list's edge — `SwipeActions` leaves that room) instead of any fill, no bar (finance tables' `Row` keeps its own `--bg-sunken` hover); in the **journal only**, the first row starts active as a hint — only while no entry is open (or the open one is filtered out of view) — until the pointer is over a row (`rowHoverHandlers` set a flag on `<html>`); other lists don't highlight their first row (it just gets a top rule — except straight under a tab bar, whose hairline would double it: Recipes, Planning list view with no filter row). Never style list rows locally
- **Lists outside the journal — one layout** (Health lists, Recipes, Shopping lists, topic pages, topic entries): entries grouped by month with `MonthGroups` (`molecules/MonthGroups.tsx` — a thin 20px Work Sans "October 2026" heading over a `--border-default` rule), then `EntryListCard` rows **flush** with the list's edge (no side padding, no chevron, no first-row highlight): the title in `--text-secondary`, an optional muted line under it, "Oct 6" muted on the right, hairlines between rows (in the dashboard widgets and the Today lists, none under the last row). - **Checkmarks — one look everywhere** (the user's favourite; never restyle): ticked = an accent **check-circle** (a ring with the tick breaking out of it — stroke only, never a filled disc), unticked = a plain grey ring (`--control-border`). - **No `window.confirm`** — Safari on iPad blocks pop-ups by default, silently returning `false`. Use inline state-based confirmation or delete directly. Never use `window.confirm` / `window.alert` / `window.prompt`.
- **TipTap node views with overlays** — Always portal overlays (`position: fixed`) from TipTap `NodeViewWrapper` to `document.body` via `createPortal`. The node view DOM can create stacking contexts that trap pointer events.

### Multi-Tenant Schema-per-User Database

Each user gets an isolated PostgreSQL schema. This is **not** row-level security.

```
PostgreSQL Database
├── public schema (shared)
│   ├── accounts - authentication + encryption params
│   ├── sessions - split-token sessions (selector + verifierHash)
│   └── schema_counter - atomic counter for unique schema names
│
├── usr_1_a1b2c3 (user 1's isolated schema)
│   ├── _migrations - schema version tracking for JIT migrations
│   ├── settings - key-value store (JSONB)
│   ├── taxonomies - topics: name + icon in an encrypted payload, colour and order readable
│   ├── posts - encrypted content + metadata (BYTEA)
│   └── post_taxonomies - many-to-many relationships
│
└── usr_2_d4e5f6 (user 2's isolated schema)
    └── ... same tables
```

**Schema naming**: `usr_{counter}_{random_hex}` — NOT derived from user info for security.

**Shards** (`server/src/db/shards.ts`, runbook `docs/SHARDING.md`): user schemas can live on several databases. The main database (`DATABASE_URL`) keeps accounts, sessions and every shared table and is shard 1; extra ones come from `SHARD_DATABASE_URLS` (`2=postgresql://… 3=…`); `accounts.shard_id` says where a schema lives (added at startup, default 1); new accounts go to the first shard under `SHARD_CAPACITY` (5000). **Tenant SQL always goes through `tenantDb(schemaName)`** (or `shardClient(id)`), never the main `prisma` client — `tenantQueries.ts`, `schemaManager.ts` and the maintenance scripts do; shared tables (`public.*`) always use `prisma`. A tenant query must never touch `public.*` (different database). Scripts close pools with `disconnectShards()`.

### Two-Layer Security Model

1. **Authentication Layer (Server)**: bcrypt hash (12 rounds, run in worker threads by `services/passwordHasher.ts` — never on the main thread) of a **derived sign-in secret**, split-token database sessions with immediate revocation, optional TOTP 2FA
2. **Encryption Layer (Client)**: AES-256-GCM with auto-generated master key wrapped by password-derived KEK (PBKDF2-SHA256, 600k iterations)

Password changes only re-wrap the master key (instant). Data is never re-encrypted on password change. No tab keeps a key wrap, so a refused change (wrong 2FA code, 429) leaves nothing stale behind: the next try fetches the wrap again (`passwordSource`). A password change can also be confirmed with a passkey touch, which opens the key for the new wrap (the old password isn't needed).

**Key wraps are bound to their purpose.** The password (KEK) wrap must open with its purpose AAD (`kek-wrap`) — the old no-AAD fallback and the `POST /api/auth/key-wrap` upgrade are gone. Only the recovery-key unwrap keeps a no-AAD fallback (those wraps can't be re-wrapped without the recovery key, and a server can't forge one). `deriveKEK` refuses any salt that isn't 16 bytes (the server schemas too): a server could otherwise send the sign-in secret's salt, making the KEK equal to the `authSecret` the client sends, and slip in a master key of its own. The KEK iteration count from the server must be 600k–2M (`checkKekIterations`, in every unwrap path)

**The server never receives the password or the recovery key** (`shared/src/crypto/authSecret.ts`). Either one would let it unwrap the master key it stores. Instead:
- `authSecret = PBKDF2(password, "chronicles:auth:v1:" + normalizedEmail, 600k)` (`deriveAuthSecret`) is what `/register`, `/login` and every password-confirmed action (change password/email, recovery key, 2FA enable/disable, delete account) send — `authSecret`, `currentAuthSecret`, `newAuthSecret`. It uses a different salt from the KEK, so it doesn't give the KEK. Its salt is the email, so `/change-email` sends a new secret too. Password rules (`passwordSchema`) are checked **on the client**; the server only checks the 64-hex shape
- Stored as `auth1$` + bcrypt(authSecret). Nothing else is accepted: the client never sends the password, whatever the server answers (`loginSchema` is strict, so a body carrying one is refused), and a pre-upgrade bare bcrypt hash can't sign in — `checkStoredCredentials()` signs out any such account at startup and logs its id (it recovers with its recovery key)
- Recovery sends `recoveryProof = PBKDF2(recoveryKey, recoveryKeySalt, 600k)` (`deriveRecoveryProof`; the salt comes from `/recovery-params`, with a stable decoy for unknown emails). The server stores `v2$` + SHA-256(proof), so a leaked row can't be replayed; older rows are sealed at startup

### TOTP Two-Factor Authentication

Implemented via `otplib` — no external services required.

**Login flow when 2FA is enabled:**
- `POST /api/auth/login` returns `{ pendingToken, requires2FA: true }` instead of a session — unless this browser is trusted for the account (see **Remember this browser**), in which case the session is issued without a code
- Client shows OTP screen; user enters code from authenticator app or a backup code
- `POST /api/auth/login/2fa` verifies the code and issues the real split-token session
- Pending tokens have a 5-minute TTL and live in the shared sign-in state (kept by the token's SHA-256; see **Several server instances**)
- A TOTP code is accepted once (its time step is raised atomically with `sharedState.advance`, so two instances can't both accept it); 10 wrong codes lock that account's 2FA for 15 minutes (the third lock in a day, for 24 hours — and so do 30 wrong codes in a day however they're spread, `countTwoFAFailure`: strikes alone were dodged by stopping at 9 a window). Both are in the shared sign-in state, like pending tokens
- The pending token survives a wrong code (retry on the same screen) and is spent only when a code is accepted. The code screen has **Back to sign in** (`cancel2FA` in `AuthContext`); a session that has expired sends the user back to the sign-in form with a note instead of leaving the screen stuck
- `POST /api/auth/recover` on a 2FA account also needs an authenticator/backup `code` (answered with `requires2FA: true` once the recovery proof checks out)

**Setup flow (Settings → Security):**
1. `POST /api/auth/2fa/setup` — generates TOTP secret + QR code (not saved yet)
2. User scans QR code and enters confirmation code
3. `POST /api/auth/2fa/enable` — needs the **current password** (as `currentAuthSecret`) and refuses if 2FA is already on (replace = disable first); verifies code, saves the secret (AES-GCM-sealed with `SECRETS_ENCRYPTION_KEY` when set), issues 8 one-time backup codes (stored salted + scrypt-hashed; old SHA-256 hashes still verify; a used code is removed with one conditional `array_remove` UPDATE so concurrent requests can't spend it twice)
4. `DELETE /api/auth/2fa` — disables 2FA; needs the password **and** a current authenticator or backup code

**Schema**: `totpSecret` and `totpEnabled` added to `accounts` table.

### Split-Token Session Strategy

Instead of storing a single token, sessions use a **Selector + Verifier** pattern:
- **Selector** (12 hex chars): DB lookup key (indexed)
- **Verifier** (32 hex chars): Only SHA-256 hash stored in DB; raw verifier sent to client
- **Cookie path**: Enforces `X-Requested-With` header for CSRF protection
- **Bearer path**: For React Native (no CSRF risk from secure storage)
- **Activity debounce**: `lastActiveAt` only updated if 5+ minutes stale (fire-and-forget)
- **Idle expiry**: a session unused for 2 hours (`SESSION_IDLE_MS`, `isSessionIdle` in `middleware/auth.ts` — a tab ends its own session after 15 minutes away, so this bounds sessions nobody is using; the app pings `/auth/me` while someone is at the page, `useIdleSignOut`) is revoked (`'idle'`) on its next use and answered 401 "Session expired", whatever its 7-day expiry — checked after the verifier, so a selector alone can't end it; the Sessions list leaves idle ones out

### Recovery Key System

The master key is wrapped with two different keys:
1. **Password-derived key** (PBKDF2) — for normal login
2. **Recovery key** — for password recovery

At registration:
- Client generates a random master key and recovery key (32 bytes each)
- Master key wrapped with password-derived key (stored as `encryptedMasterKey`)
- Master key also wrapped with recovery key (stored as `recoveryWrappedMK`)
- Recovery key shown once to user — must be saved
- The server stores only a check of a PBKDF2 proof of the recovery key (see Two-Layer Security Model); the key itself never leaves the browser

### Encryption Specification

```
Algorithm: AES-256-GCM
IV: Random 12 bytes per encryption operation
Key Derivation: PBKDF2-SHA256, 600,000 iterations (OWASP 2024)
Salt: 16 bytes random per user
Master Key: Non-extractable CryptoKey (cannot be exported from Web Crypto)
Content: Encrypted client-side, stored as BYTEA in PostgreSQL. Content and metadata
         are a bound pair, bound to the entry: each half's AAD is
         `chronicles:post:v3:<part>:<entry id>:<other half's IV>`, so they are always
         saved together and one entry can't be served as another. A new entry
         reserves its id first (`POST /api/entries/ids`, `encryptNewPost`; the server
         creates it only under an id it handed out and hasn't used — each reservation
         is recorded and used up on create, `post_id_reservations`) and every write says `format: 3`.
         v2 (pair-bound) and pre-AAD entries open only until the account's one-time
         move (`services/entryReseal.ts`, `PUT /api/entries/reseal` — 100 at a time,
         updated_at kept, skipped if the entry changed since loading) writes the sealed
         marker `entriesSealV3`; after that they're refused. Server and client both
         refuse plaintext posts. Reserved ids are checked: one an entry already has,
         or one the server handed out before, is refused (`reserveEntryId`)
Markers: the seal markers (`settingsSealV2`, `entriesSealV3`, `topicsSealV2`,
         `dosesSealV2`) live on the server, which could leave one out to reopen the
         older readers. `services/sealedFormats.ts` backs them: once a browser has
         seen a marker it keeps counting it (localStorage, kept through sign-out),
         and from `LEGACY_FORMATS_UNTIL` (2027-01-01) the older forms never open
Created: an entry's creation time is sealed in its metadata (`_createdAt`, set by `encryptNewPost`, kept by `encryptPost`; backdated creates set it to the day they send) and wins over the server's readable created_at on decrypt
Storage: per account, encrypted entries are capped at ENTRY_STORAGE_LIMIT_MB (200)
         and finance payloads at FINANCE_STORAGE_LIMIT_MB (50) — 413 over the cap
Topics: an entry's topic lives only in its encrypted metadata (`_taxonomyId`). The client's
         entries API strips `taxonomyIds` and the server ignores it, so no plaintext
         entry→topic link is written; old `post_taxonomies` rows can be removed with
         `npm run clear:topic-links -- --apply` (server; dry run without the flag)
Search: Client-side on decrypted data (no server-side search tokens)
```

## Important Implementation Notes

### Entry sync (browser cache)
`entriesApi.getAll()` keeps the journal **as ciphertext** in IndexedDB (`services/entryCache.ts`, database `chronicles-entries`, rows keyed by a per-account `scope` the server derives from the schema) and downloads only what changed: `GET /api/entries/cursor` (`{ cursor, scope }`), then `GET /api/entries/changes?since=` (`{ entries, deleted, cursor }` or `{ reset: true }`). Server side, a trigger (`public.chronicles_post_changed`, per database; `postSyncStatements` per schema, added on first use by `ensurePostSync`) stamps every insert/update with `change_xid` (the transaction id) and writes deletions to `deleted_posts`, so **every write path is tracked automatically — never bypass the trigger** (no `ALTER TABLE … DISABLE TRIGGER`, no `session_replication_role`). The cursor is the snapshot xmin taken before reading, so in-flight writes are re-sent, never skipped. `deleted_posts` is trimmed to its newest 10,000 rows once it passes 12,000 (`pruneDeletedPosts`, run after each delete; indexed on `id` and `change_xid`): the trim leaves one row with id 0 holding the newest transaction id trimmed, and a `/changes` cursor at or below that mark — or one with more than 5,000 deletions to list — is answered `reset`. A trimmed id stays spent all the same: **every id handed out is recorded** (`post_id_reservations`, per account) and creating an entry uses up its reservation in the same statement (`insertPostSql`), so an id is created at most once whatever is trimmed or however the sequence moves; reservations nobody used go after 7 days (`RESERVATION_DAYS`) and an account holds at most 2,000 (`MAX_RESERVATIONS`, oldest dropped first), both in `reservePostIds`'s one statement. Older accounts get the table on first use (`ensurePostReservations`, after `ensurePostSync`; `npm run migrate:tenants -- entry-ids`), seeded with the newest 500 ids handed out that no entry has and no deletion names (`RESERVATION_SEED_WINDOW`), so a tab open across the upgrade still saves. A full download happens on first use, on `reset`, for another scope, and weekly. Lock keeps the cache (nothing decrypted is in it); `logout` (`AuthContext`) erases it with `clearEntryCache()` before deleting the other IndexedDB databases. Without IndexedDB (jsdom tests, some private modes) it's the plain paged download. `loadtest/sync-check.mjs` checks sync against a fresh full load under concurrent writes.

### Journal saves (no duplicate entries)
In `JournalView`, every save — the 3s autosave, the wellness autosave and Save entry — runs through one queue (`runSave`), one at a time. The entry being written is `entryIdRef`, set the moment a create returns (`adoptCreatedEntry`), so the next save updates it instead of creating a second copy; Save clears the pending autosave timer. `editSessionRef` moves on whenever the editor shows another entry or a blank new one (`showBlankEntry`), and a save queued for the old one is dropped (this also stops a second click on Save). The load effect switches the editor only when what it shows changes (`shownRef`: `e<id>` / `new:<topic>:<fields>`), never on store updates, so a save or sync can't overwrite what's being typed. `Editor` forgets the HTML it last emitted once the parent hands it anything else, so reopening an entry whose text matches what was typed still loads it. `QuickEntry` guards its save with a ref, not just state.

### A view that fails to show
`atoms/ErrorBoundary.tsx`: every signed-in page is wrapped in one (`R` in `App.tsx`, reset by the address, with links to Journal and Settings and a Reload), the floating extras (reminders bell, chat, running timer, notice banner) each in a silent one (`fallback="none"`), and `main.tsx` has a last-resort one — so one entry holding something a view didn't expect can no longer blank the whole app on every load. The error's text is never shown (it can hold decrypted text). `IdleGate` and `SessionEndedGate` stay outside the page boundaries. **Import Entries** leaves out columns named like a field that holds a list or object (`STRUCTURED_FIELDS` in `utils/csv.ts`: items, scheduleTimes, repeatDays, steps…) — an import writes text and yes / no only; add a new list-valued field's key there. Readers of such fields check `Array.isArray`.

### Deleting entries
Every list's delete (swipe, editor, bulk) goes through `deleteEntryWithImages` (`utils/entryActions.ts`): the entry leaves the store at once, then the server delete runs. If it fails the entry is put back and `showFlash` (`services/flashNotice.ts`, shown by the `FlashNotice` bar mounted once in `App.tsx`) says "Couldn’t delete that entry, so it’s back in the list. Try again."; a 404 counts as already deleted. Use `showFlash` for other short failure notes rather than adding another toast.

### Entry Pagination
`entriesApi.getAll()` (without the cache, and for full downloads) pages `?v=2&limit=5000&offset=…` (server orders by `created_at DESC, id DESC`, offset uncapped) while the answer's `more` is true, each next offset where the last page ended, skipping ids repeated across pages — one request for most journals. A page also stops at 16 MB of ciphertext (`getPostPage`, sizes read first; always at least one entry), `/changes` answers `reset` above that, and one account may run 3 list requests at once per instance (429 + Retry-After; `readGate` in `middleware/readGate.ts`, which frees a slot only once the response was sent or the connection closed — it also caps the finance, doses/all, per-day doses (`doses-day`, 4 — the dose caps are per account, so one day can hold all 20 MB), topics and settings lists and single-entry reads (`entry`, 6), each in its own lane; the client asks a briefly deferred GET again, `sendWhenFree`) — so no request holds an account's whole storage cap in memory. Without `v=2` (older clients) the bare array comes back. Never go back to a single capped request: topic filtering, search, reports and Export All rely on every entry being in the client store, and entries past the cap silently vanished.

### Imports
Bulk creates go through `POST /api/entries/batch` (up to 100 entries, one transaction, all or none) via `entries.createMany` (50 a request, under ~3.5 MB). One request per entry hit the per-account limit at ~1,430 entries.

### Server capacity (see `docs/SCALE_TEST_REPORT.md`, harness in `loadtest/`)
- **Never hash on the main thread**: `bcryptjs` blocked the event loop ~400 ms per hash and stalled every request. Use `services/passwordHasher.ts` (`BCRYPT_WORKERS`, `BCRYPT_MAX_QUEUE`; a full queue answers 503 + Retry-After)
- **A capped write is one trip to the database** (`lockedStatement` in `tenantQueries.ts`): the account's advisory lock, then ONE statement that checks the cap and writes (`updatePostCapped`, `createPostCapped`, `upsertSettingCapped`, `upsertDoseRecordCapped`). `withTenantLock` runs a callback between statements, so each is its own trip from Node (BEGIN, lock, sum, write, COMMIT) with a pooled connection held throughout — entry saves ran at about a quarter of reads that way. The statement starts after the lock is held, so its snapshot sees the previous holder's writes; a refused write does its second look (which cap? 404 or full?) outside. A new single-row capped write uses it; `withTenantLock` stays for the multi-row paths (batch import, re-seals, finance, topics)
- **Database pool**: `DB_POOL_SIZE` (default 5, unless `DATABASE_URL` sets `connection_limit`) and `DB_POOL_RECYCLE_MINUTES` (default 30). Each connection caches every user schema it touches (~50 KB per user), so connections are swapped for fresh ones (the new pool is opened before it takes over); `DB_KEEP_WARM_MINUTES` (default 4, 0 = off) pings the database so a serverless one (Prisma Postgres sleeps, ~15 s to wake) never times out saves or sign-in checks. `withTenantLock` queues one account's writes in the process before taking a connection — a transaction waiting on the advisory lock holds its connection, and a burst once filled the pool. Import `prisma` from `db/prisma.ts` (a proxy to the current client), never construct another `PrismaClient`
- **Backups**: `checkBackupLockCapacity` (`db/backupCheck.ts`) warns at startup / every 6 h when tables outgrow `max_locks_per_transaction` — pg_dump locks every table and failed at ~1,000 users on defaults
- **JIT migrations read before they ALTER**: an `ALTER TABLE … IF NOT EXISTS` still takes an exclusive lock; check the catalog first (`topicColumnsMigrated`)

### Typing performance (journal editor)

## Security Hardening

### Content Security Policy (CSP)
Applied via Express middleware (`server/src/middleware/security.ts`):
- `default-src 'self'` — only same-origin
- `script-src 'self'` — no inline scripts
- `style-src 'self' 'unsafe-inline'` — required for styled-components
- `img-src 'self' data: blob:` — images from same origin and data URIs
- `connect-src 'self'` plus Open-Meteo (dashboard weather), Google Calendar, the media cover catalogues (Open Library + archive.org, iTunes Search + mzstatic, TVmaze, Wikipedia — see **Media journal**), the user's R2 bucket (`*.r2.cloudflarestorage.com` — the account ID is encrypted, so it can't be pinned), and the AI providers (`api.anthropic.com`, `api.openai.com`, and `bedrock`/`bedrock-runtime` hosts for each region in `BEDROCK_REGIONS`, `shared/src/validation/awsRegions.ts` — never `*.amazonaws.com`; AI settings reject unlisted regions)
- `frame-ancestors 'none'` — prevent clickjacking; plus `base-uri 'self'`, `form-action 'self'`, `object-src 'none'`
- **Trusted Types** on pages: `require-trusted-types-for 'script'; trusted-types default dompurify 'allow-duplicates'` (`trustedTypesDirectives` in `middleware/security.ts`; left off `/sw.js` only, since the service worker takes its own response's CSP and loads Workbox with `importScripts` — every other path keeps it, and a missing `/sw.js` is a 404, never `index.html` under the worker's CSP). A plain string at an HTML / script sink goes through the client's **default policy** (`client/src/security/trustedTypes.ts`, imported first in `main.tsx`): HTML is DOMPurify-sanitized (`TRUSTED_HTML_CONFIG` keeps the drawing node's `svgcontent` attribute — anything the editor writes must survive it), script URLs must be same-origin, strings as code are refused. Don't add `innerHTML` / `DOMParser` / `eval` paths; read text off a DOMPurify fragment instead (`stripHtml`). Checked in real Chromium and WebKit with the policy enforced: the editor (drawings included), paste sanitizing, the share stripper, the service worker and every public page
- **DoS bounds**: encrypted fields must be strict base64 (a ciphertext at least a GCM tag, an IV exactly 12 bytes — `ciphertext()` / `IV_FIELD` in the shared schemas), and every stored entry / finance row counts `ROW_OVERHEAD_BYTES` (512) toward its storage cap, so the caps bound row counts too. `writeGate` (`middleware/rateLimiter.ts`) allows 16 writes in flight per account (429 + Retry-After), before entry bodies are read. Regexes on request text must be linear: the share media scan once backtracked quadratically (`url(` + spaces froze the server) — keep each quantifier followed by a different class, and length-check before scanning (zod runs a refine even after `.max` fails). zod is 4.x across the workspace (root `overrides`)
- **Concurrency slots are held until the work is over** (`middleware/slot.ts`, `releaseWhenSettled` — used by `readGate`, `writeGate` and the public shelf's per-token cap): a slot is freed when the response finished, or — for a client that hung up — only once the handler has answered. Freeing on the socket's `close` let a client open requests and hang up, running any number at once past every cap. A new gate uses it too, never `res.on('close', release)`
- **Stored only what can be stored / opened**: key wraps are exactly 64 base64 characters and their IVs 16 (`wrappedKeySchema` / `saltOrIvSchema` — sign-up, password change, recovery, a new recovery key), so a wrap no password could open is never saved over a good one; usernames and setting keys hold no control characters, and a setting value or share with a zero byte (or nested too deep to serialize) is a 400, not a 500 (`storableJson`). A session token is exactly 44 hex characters (`sessionCookie` takes strings only — cookie-parser turns a `j:` value into an object)
- `Cross-Origin-Opener-Policy: same-origin` on every response (the Google Calendar sign-in is a full redirect, never a pop-up)
- Every `/api/*` response is `Cache-Control: no-store` (set in `securityHeaders`; the ICS feed overrides it) so wrapped keys, ciphertext and settings never land in the browser's disk cache
- `Permissions-Policy` keeps `microphone=(self)` (voice dictation); camera, geolocation etc. are off

### Account-change rules
- The wrapped master key + salt leave the server **only in the answer to a checked password or passkey**: `/login`, `/login/2fa`, `/recover`, `/password-wrap` (the password wrap — never the recovery wrap — against `currentAuthSecret` **and, with 2FA on, a code**, for one named action, counted in the confirm lockout. It answers with a single-use `confirmToken` for that action, so the action itself doesn't ask for the one-use code again. A tab never keeps the wrap, so every password-confirmed re-wrap fetches it here), and a passkey's own wrap from `/passkey/verify` and `/confirm/verify`. **`/me` returns the user only** — it used to return the wrap to any live session, so a stolen session cookie was enough to guess the password offline with no lockout. Never by an unauthenticated lookup. There is no `/auth/salt`
- Changing the email (`/change-email`), the recovery key (`/recovery-key`) or turning on 2FA (`/2fa/enable`) requires the **current password**, like change-password and 2FA disable — a signed-in session alone must not be able to lock the owner out. With 2FA on, change-password, change-email, the recovery key and account deletion also need an authenticator or backup `code` (`secondFactorGate`; Settings shows a 2FA code box), so a stolen session plus a phished password isn't enough. Password change, email change, recovery-key change and turning 2FA on or off all sign out every other session. **A passkey touch can confirm these instead** (not change-email — its new sign-in secret needs the typed password): `POST /api/auth/confirm/options { action }` issues a challenge tied to that action and session, `POST /api/auth/confirm/verify` checks the touch (user verified) and answers a single-use `confirmToken` (5 minutes, that action, that session — `services/confirmTokens.ts`, spent atomically with `sharedState.takeToken`) plus that passkey's wrap; the action's request sends `confirmToken` in place of `currentAuthSecret` + `code` (`confirmIdentity` in `routes/auth.ts`; the schemas take exactly one of the two, `CONFIRM_ACTIONS`). Wrong touches count in the session's confirm lockout. Every such form's field reads **“Enter your account password”** (`molecules/ConfirmIdentity.tsx`, with **Use a passkey** when the account has one this browser can use), never just “Confirm”
- Settings are forgotten with `DELETE /api/settings/:key` (`settings.remove`) — sealed settings can't be saved as `null` — as removing the AI or R2 credentials does. Settings writes check their caps (500 keys, 8 MB in all) under `withTenantLock`
- Authenticator secrets stored readable (before `SECRETS_ENCRYPTION_KEY` was set) are sealed at startup (`sealStoredTotpSecrets`); without the key the server warns how many are readable. A server without the key can't open a sealed secret (e.g. a dev server on the live database): an authenticator code then gets a 500, **uncounted** — it never adds to the lockout, which is shared through the database — and startup logs how many sealed secrets it can't open; backup codes still work. Every server on one database needs the same key
- Google OAuth: the signed `state` also carries the hash of a nonce kept in an HttpOnly `SameSite=Lax` cookie (`__Host-chronicle_oauth`), so the callback only succeeds in the browser that started the flow
- `trust proxy` is on in production (`TRUST_PROXY`, default 1 hop) so per-IP rate limits see the real client IP behind Render's proxy
- Lockout counters (sign-in per email, second factor, and the password-confirmed actions **per session** (`confirmKey`: `<account>:s:<selector>` — per account, a stolen session could lock the owner out of changing the password) — 10 wrong passwords / 15 min, the third lock within a day locks for 24 hours, as do 30 wrong ones in a day however they're spread — every failure counts toward the day's total: `passwordFailed` / `strikeTwoFALock` / `countTwoFAFailure`) count an attempt **before** the slow check, so a parallel burst can't pass the cap; pending 2FA sign-ins are cancelled on password change, recovery, 2FA disable and **Sign out everywhere**. **Sign-ins in flight** (`routes/authState.ts`): a password or passkey sign-in holds a short-lived token from before its check until its session exists (`beginSignIn` / `signInStillWanted`; a 2FA sign-in's pending token is taken only once its session exists), and Sign out everywhere, a new recovery key and removing a passkey call `cancelSignIns` **before** revoking the sessions — so a sign-in that was mid-check can't leave a session behind. Wrong 2FA codes count per bucket (`twoFABucket`): a signed-in session (password-confirmed actions) and a known device each get their own, strangers share the account's — so someone holding a phished password can't lock the owner out of changing it
- Signing in again on a browser revokes the session its cookie still held (`revokeBrowserSession`); the auth middleware answers "Session revoked" / "Session expired" only once the verifier matches (a bare selector learns nothing)
- Server-held secrets sealed with `SECRETS_ENCRYPTION_KEY` (`tokenCrypto`) are bound to their row: `b1:iv:ct:tag` with an AAD — `totp:<account id>`, `google:<account id>`. Older unbound TOTP secrets are re-bound at startup (`sealStoredTotpSecrets`), Google tokens on next use
- Invite links last `INVITE_VALID_DAYS` (30) from approval (approving again issues a fresh one); `REGISTRATION_WHITELIST` is honoured only when `NODE_ENV=development` — the same test that marks cookies Secure, so a host with `NODE_ENV` unset or `staging` ignores it too (a listed email needs no code, so anyone could claim it)
- Sign-in has a per-email cap on top of the per-IP limit: 10 wrong passwords lock that email for 15 minutes (shared sign-in state, keyed by the normalized email whether or not an account exists, so a lockout reveals nothing). A browser that has signed in to that email carries a signed HttpOnly **known-device** cookie (`__Host-chronicle_device`, 90 days, HMAC of email + nonce **and the password hash and 2FA state it was earned under**, `deviceMac`) and counts its failures in its own bucket, so a stranger's guesses can't lock the owner out of their own browser — the password and 2FA are still checked. Turning 2FA on (or off) therefore ends every cookie from before — while 2FA was off a password alone earned one, as many times as wanted, and each would have had its own wrong-code bucket — and reissues one to the browser that made the change. **A sign-in looks again once its session exists** (`sessionStillEarned`, `/login` and `/login/2fa`): if the password hash or 2FA setup it checked is no longer the stored one (a change landed during the ~0.4 s hash), the session is revoked and the sign-in refused, so none outlives "sign out everywhere"
- Public share links hold plaintext: revoking one **deletes** the row, deleting an entry deletes its shares (`deleteSharesForEntry`, before and again after the entry goes; creating a share re-checks the entry afterwards — so a link made during a delete can't outlive its entry), and revoked/expired rows are purged at startup and every 6 hours (`purgeDeadShares`)
- The **public shelf** (`public.public_shelves`, one row per account) holds plaintext by the user's choice too: Turn off hard-deletes it and the account FK cascades; `putPublicShelfSchema` strips everything but the shown fields and takes JPEG data-URL covers only (≤120 KB each, ≤1000 items as a sanity bound, `PUBLIC_SHELF_LIMIT_MB` 6 the real cap → 413); the PUT's 8 MB parser runs only after `authMiddleware`; the public GET serves **24 items a page, filtered, sorted and sliced in SQL with bound values** (never the whole list), under `publicShelfLimiter` (240 / 15 min per IP) with `Cache-Control: private, no-cache` (the browser keeps its copy but asks every time — with `max-age=60` a change, above all taking an item off, went unseen for a minute; the open public page also looks again when its tab is shown) + `ETag`; public share and shelf pages carry `X-Robots-Tag: noindex, nofollow`
- `DELETE /api/auth/account` deletes the account (tenant schema dropped, then the account row; sessions, shares and the calendar integration cascade). Needs the password, plus a 2FA code when 2FA is on. Settings → Account → Delete account (inline confirmation). Images in the user's R2 bucket and events already pushed to Google Calendar are not touched
- Recovery decoys use `SECRETS_ENCRYPTION_KEY`, else an HMAC of `DATABASE_URL`, so they stay stable across restarts
- Account enumeration: `/recovery-params` answers an unknown email with **stable** decoy params (HMAC of the email, same sizes as real ones) — never random-per-request. Sign-up must say an email is taken (no email verification), so `/register` has its own `registerLimiter` (10/hour per IP)

### Several server instances
The server can run as more than one instance behind a load balancer. Everything sign-in related that instances must agree on lives in Postgres (`services/sharedState.ts`, the UNLOGGED `public.auth_state` — a database crash empties it, like a restart emptied the old in-memory maps): pending 2FA sign-ins, the last TOTP step per account, the sign-in / 2FA / password-confirm lockout counters, and the stores behind `authLimiter`, `strictLimiter`, `registerLimiter`, `shareLimiter`, `publicShelfLimiter`, `betaLimiter` and `icsFeedLimiter` (`sharedRateLimitStore`). Each check is one atomic statement, so attempts are still counted before the slow check across instances. Passkey challenges (sign-in, adding one, confirming an action) and passkey confirmation tokens live there too, each spent atomically (`takeToken`); passkeys and trusted browsers are ordinary tables (`public.passkeys`, `public.trusted_devices`). `apiLimiter` stays per instance on purpose (it runs on every request; a coarse cap, so N instances allow up to N × 1500). `SHARED_STATE=memory` keeps all of it in the process (one instance only); tests run that way. Never add a new in-memory map of sign-in or security state — use `sharedState`. `loadtest/multi-instance-check.mjs` (through `loadtest/rr-proxy.mjs`) checks it across two instances. Instance-local caches that only skip repeated work (JIT migration sets, the schema → shard map) are fine.

### Rate limiting
- `failedAuthLimiter` (first on `/api`, per IP, in memory): only requests answered 401 count, 200 / 15 min, then 429 before any session lookup — a flood of made-up tokens can't keep the connection pool busy
- `apiLimiter` (`server/src/middleware/rateLimiter.ts`): 1500 requests / 15 min **per account** on data routes (auth routes have their own stricter limiters; `strictLimiter` — 5 / 15 min — counts each route separately, keyed by the matched route so case or a trailing slash can't open a new bucket, so typos on one action don't block another). It must stay well above normal SPA use plus bulk actions (imports, bulk edits, dose → Meals sync) — 300 locked real users out
- Client: identical in-flight GETs share one request (`request` in `services/api.ts`; followers get a `structuredClone`). A 429's `Retry-After` is carried on `ApiError.retryAfterSec`; initial loads (`useInitializeData`, `JournalView`) retry with `retryDelayMs` — Retry-After on 429 (5s–15min), else 10s→60s backoff — and never fall back to an empty journal

### CSRF Protection
- Web requests require `X-Requested-With: XMLHttpRequest` header
- Mobile requests use `Authorization: Bearer` (no CSRF risk)
- Explicit branching in auth middleware — never mixed

### Password Strength
- Minimum 12 characters; uppercase, lowercase, a number and a symbol (`passwordSchema`, `shared/src/validation/schemas.ts`)
- **And hard to guess**: `newPasswordProblem` (`shared/src/validation/passwordStrength.ts`) runs the rules, then `passwordStrength` — an estimate in bits (length × the character pool, less what patterns give away: ~150 common passwords and words with l33t swaps undone, the email's name part and the username, repeats incl. a repeated chunk, runs like abcd / 1234, keyboard rows, years) scored 0–4 (Too weak / Weak / Fair / Good / Strong); a new password must be **Good** (`MIN_PASSWORD_SCORE` 3) and must not contain the email name or username. Used by sign-up (`RegisterForm`, which before this didn't require the symbol), Settings → change password (and `ChangePassword`) and recovery (`RecoverView`)
- **Meter**: `PasswordStrengthMeter` (molecule) under every new-password field — four 4px rules filling up (red → amber → accent), the word on the right, one tip under them (`role="status"`); nothing until something is typed
- All checked on the client — the server never sees the password, so it can't. Nothing about the password leaves the browser (no breach-list lookups)

## State Management

**Zustand** for client state (not Redux):
- `uiStore` — Search filters, sidebar state, theme colors, selected entry
- `entriesStore` — Decrypted entries cache, topics, loading state

**React Context** for auth and encryption:

### Sign-in, the key and idle sign-out (no Lock, no stored key)
Plan and as-built notes: `docs/AUTH_REDESIGN_PLAN.md`. **A tab either holds the master key and is signed in, or it shows sign-in. There is no lock screen, no "signed in but locked", and nothing that opens the journal is ever stored** — not in the browser, not on the server.
- **Master key**: a **non-extractable CryptoKey** in a React ref (`EncryptionContext`), memory only. `isUnlocked` = this tab holds it. `clearKey()` drops it with every decrypted entry, topic, private setting and config in the stores — always as part of ending the session, never a state of its own. Views show their spinner until the data is in (`useInitializeData` returns `{ isReady, isLoading }`)
- **Three ways to open it**, each a wrap of the same key: the password (KEK, `kek-wrap`), the recovery key (`recovery-wrap`), a passkey (below). **No tab keeps a key wrap**: `login` / `submitTotpCode` hand it straight to `unlock`, which uses it and lets it go (a cached one went stale when the password changed in another tab, and is one more thing in memory that opens the journal). A re-wrap with the typed password fetches it each time (`passwordSource(password, email, action, code)` → `POST /auth/password-wrap`), and the source carries that request's `confirmToken`. Another wrap of the key (new password, recovery key, passkey) is made from a `KeySource` — `{ kind: 'password', password, params }` or `{ kind: 'passkey', prf, wrap }` — through `rewrapWith` / `recoveryKeyWith` / `passkeyWrapWith`; the extractable copy exists only inside those calls
- **Passkeys** (`routes/passkeys.ts`, `db/passkeyQueries.ts`, `services/webauthn.ts`; client `services/passkeys.ts`, `organisms/PasskeySettings.tsx`): WebAuthn with the **PRF extension** — the authenticator returns 32 secret bytes, the same each time for that passkey, only after its fingerprint / face / PIN check. HKDF-SHA256 of them (`derivePasskeyKek`, info `chronicles:passkey-wrap:v1`) wraps the master key, AAD `passkey-wrap:<credential id>` (no fallback form). The server stores, per passkey (`public.passkeys`, ≤10 an account, cascade): public key, counter, name, sync flag, `wrapped_mk` + `wrap_iv`. **The PRF secret never reaches the server**: the client builds its answers without `clientExtensionResults` and the schemas drop any that arrive. Sign-in is one ceremony — `POST /auth/passkey/options` (public, no email, no credentials listed, so it says nothing about any account) then `/auth/passkey/verify` (signature, single-use challenge, origin, RP ID, **user verified**), which makes the session and returns that passkey's wrap; the page unwraps to a non-extractable key and zeroes the secret. One touch is both factors: no 2FA code. A passkey that can't do PRF is **refused at adding** (it could sign in but never open the journal). Adding / removing is confirmed like the other sensitive actions, and **removing one signs out every other session** (one its device already made must not outlive it); the password is checked before anything is made on the device, and a passkey the server refuses is dropped from the device where browsers allow (`signalUnknownCredential`). **Sign-in asks for the passkeys that worked in this browser** (`knownPasskeys` in `services/passkeys.ts`: their ids in `localStorage` `chronicles.passkeys-here-v1`, kept through a wipe — random, naming nobody; remembered when one is added or signs in here, forgotten when the server says it isn't on the account) as `allowCredentials`, so the device's own prompt opens: a password manager holding any passkey for the site (LastPass keeps the ones whose adding failed, has no PRF and can't be told to drop them) otherwise answers first with one that can't open the journal. Once a try hasn't signed in, the form offers **Use a different passkey** (`{ any: true }`, no list). At adding, a passkey whose answer says nothing about PRF (`enabled` neither true nor false — a password manager made it) is refused at once, with no second prompt. A failure before the sheet opens says what it was (`utils/passkeyProblem.ts`: too many tries, server out of reach, wrong address), never "That passkey didn’t work". Removing a passkey in Settings clears that browser's remembered ids (`forgetPasskeysHere`). A **synced** passkey's signature counter is not held to "never lower" (`checkAssertion` passes 0 for `backedUp` ones — its devices' counters don't run in step); a refused passkey's reason goes in the security log (`passkey_verify_failed`). Settings → Security → **Passkeys** (add, rename, remove, **Remove all passkeys** for a lost device; Recovery offers the same as a checkbox). **Sign-up offers one too**: after the recovery key, where the browser can use a passkey, `RegisterView` shows `organisms/PasskeyOffer.tsx` ("Sign in with one touch": **Add a passkey** / **Not now**) — the password just chosen confirms it (kept in a ref for that step only), so nothing is typed again. Both places add through `hooks/useAddPasskey.ts`. A password change or recovery leaves passkeys working (the key doesn't change). **RP ID** = the host of `APP_URL` (else `CLIENT_URL`), or `WEBAUTHN_RP_ID`: a passkey is tied to it for good, so it must be the production domain from the first passkey on. Verification uses `@simplewebauthn/server` (pinned); tests sign real answers with a software authenticator (`__tests__/routes/softAuthenticator.ts`)
- **A page that loads with a session but no key** (a new tab, a reload — `EncryptionContext`, `services/keyHandoff.ts`): it **takes the key from a tab that holds it** — a non-extractable CryptoKey passes between same-origin tabs over `BroadcastChannel`, still non-extractable (checked in Safari, Chrome and Firefox with `loadtest/key-handoff-check/`), and only to a tab whose `/me` says the same email — **and never once the browser is idle** (`browserIsIdle`, `services/activity.ts`): a tab about to sign out must not let a new one in with no password or touch. Taking the key this way is not activity (`install(key, false)`); only a real sign-in marks it. Tabs holding the key (or signing in) keep the Web Lock `chronicles-key`; where a browser has no Web Locks (Safari was found without them) the new tab asks "who is here?" and takes 800 ms of silence as nobody. **With no holder the session is nobody's**: it is ended on the server (`endSession`) and sign-in shows. With a holder that can't hand the key over, the tab shows sign-in and leaves the browser's session alone (`dropUser`). `isRestoring` is true until this is decided
- **Idle sign-out** (`hooks/useIdleSignOut.ts`, mounted once by `IdleGate` in `App.tsx`): 15 minutes with nobody at **any** Chronicles tab (`chronicles.lastActive`, shared) ends the session — `useEndSession`: `clearKey()` + `endSession()` + `/login` with "You were signed out after 15 minutes away." **Measured against the clock, never a running timer** (timers stop while a laptop sleeps): checked every 10 s, whenever the page is shown, hidden or focused, and **before any activity is counted**, so the click that wakes a laptop doesn't keep it alive. Mounting the watch is not activity. Dictation counts as being there (`noteActivity`). Switching tabs does nothing by itself
- **Three ways a session ends, and what each leaves**: **Sign out pressed** (`useSignOut` → `logout`): server logout with `forgetBrowser: true` (ends this browser's trust too), then a full wipe (`resetLocal` → `wipeBrowserData`). **By itself** — idle, a keyless page with no holder (`endSession`), or the server ending it (`SessionEndedGate`: `clearKey` + `dropUser`, never a server logout): memory and sessionStorage go, **what the browser stores stays** (the encrypted cache, sealed drafts, preferences, this browser's trust). It is ciphertext only and no wrap of the key is stored in the browser, so it opens nothing
- **The wipe takes the shared activity record too**, so `install` marks activity again after a wipe (a real sign-in only): without it a second tab — which takes the key but has seen nobody itself — read the browser as idle and ended the session for every tab (opening the public shelf right after signing in on a new browser signed the owner out, and the next save got a 401)
- **Whose browser is this?** (`services/browserData.ts`): once a key is open, `claimBrowserFor(tag)` compares a mark only that key can make (`chronicles.owner-v1`, a hash of the account tag — never the email) with the stored one. The same person keeps everything (a sign-in doesn't re-download the journal); **anyone else, or a browser with no mark, is wiped before anything loads**, and the other tabs are told. So a new account still never starts on top of the last person's data. `useFreshSignIn(email)` before every sign-in clears this tab's memory and announces who is signing in (`announceSigningIn`): a tab showing someone else drops everything at once, a tab showing the same person carries on (it shares the new session cookie)
- **Sealed drafts** (`services/drafts.ts`, `hooks/useSealedDraft.ts`, `molecules/DraftNote.tsx`): unsaved writing in the **Quick entry** and the **journal editor** is sealed with the master key (AAD `chronicles:draft:v1:<slot>`) into IndexedDB `chronicles-drafts` two seconds after each pause — never per keystroke — and offered back after the next sign-in ("You have unsaved writing from … Restore · Discard"). A found draft is never lost to new typing: writing something else while it is on offer seals the new text with the old one kept beside it (`older`), offered next. When the form unmounts, whatever is waiting is settled at once (a save followed by leaving the page leaves no draft of a saved entry). A draft is removed on a failed read only when the cipher itself refuses it (`OperationError`) — never because the key left the tab mid-read. It goes when its entry is saved, on Discard, after 7 days, on Sign out and when a different person signs in. `flushDrafts()` seals what's waiting before an idle sign-out
- **Server `/auth/logout` works without a live session**: it ends the session the cookie holds when its verifier matches (`revokeBrowserSession(req, 'user_logout')`) and **always** clears the session cookies — even for an expired, idle or revoked session. Browser calls need `X-Requested-With`; Bearer clients go through `authMiddleware`. If the server can't be reached, `chronicles.pending-sign-out` is set and the next load ends that session **before** trusting `/me`
- Older notes in this file that say "on lock" / "cleared on lock" mean `clearKey` (the session ending)

### Remember this browser (skip the 2FA code — nothing else)
`db/trustedDeviceQueries.ts`, `routes/auth.ts`; `molecules/TrustBrowser.tsx`, `organisms/TrustedBrowsersSettings.tsx`. For accounts with 2FA, on the password path (a passkey sign-in never asks for a code).
- **It skips** the authenticator / backup code at sign-in. **It never skips** the password (checked first, every time, counted in the lockout), the key derivation, or the confirmation at a sensitive action. **It stores** no key, no wrap and no password: a random token in an HttpOnly, Secure, SameSite=Strict cookie (`__Host-chronicle_trust`, 30 days), and only its SHA-256 in `public.trusted_devices` (label such as "Safari on macOS", created, expires, last used; ≤10 an account)
- **Issued** only by `/login/2fa` with `trustBrowser: true` after the **authenticator's** code (never a backup code), 30 days from then — use doesn't extend it. The box ("Don’t ask for a code on this browser for 30 days") is on the code screen, off by default
- **Checked** in `/login` only after the password has verified (a wrong password learns nothing about the token), matched on hash + account + expiry in one statement, and again once the session exists (a trust ended meanwhile leaves none behind). Each use is logged (`login_trusted_browser`)
- **Ends on**: Forget (Settings → Security → **Trusted browsers**), Sign out everywhere, a password change or recovery, an email change, a new recovery key, 2FA on or off, pressing Sign out in that browser (`forgetBrowser`). **Not** on idle sign-out, a reload or closing the browser
- The known-device cookie (`__Host-chronicle_device`) is unrelated: it only decides which lockout bucket wrong guesses count in

## UI Theme

### Styling: styled-components + CSS Variables
- All styles co-located with components using styled-components
- Components reference CSS variables first (`var(--ink, ${theme.colors.text})`) so root-level theme switches take effect without re-render
- Theme tokens in `shared/src/theme/tokens.ts` — shared with future React Native; TypeScript shape declared in `client/src/styles/styled.d.ts`
- `ThemeProvider` at app root supplies tokens; `App.tsx` injects CSS variables on mount and on theme/accent change

### CSS Variable Injection (App.tsx)
Three sets of variables are written to `:root`:
- **Static** (`STATIC_CSS_VARS`): radii (`--r-sm/md/lg/xl`), spacing (`--s-1` … `--s-10`), font families (`--serif/--sans/--mono/--brand/--ui`)
- **Theme** (`LIGHT_CSS_VARS` / `DARK_CSS_VARS`): color tokens that flip between Paper and Midnight — `--paper`, `--ink` × 4, `--rule`, `--btn-primary`, `--accent-fill`, semantic colors, shadow values
- **Dynamic accent**: on every header-color change, derives `--accent`, `--accent-hover`, `--accent-tint`, `--accent-stroke`, `--h-active`, `--h-active-ink`, and legacy `--focus`

### Customizable Colors
- **40+ header accent colors** (Dark, Navy, Gold, Coral, Teal, Steel Blue, etc.) + transparent
- Colors derived programmatically: hover (15% darker), tint (10% opacity), stroke (desaturated muted variant for borders)

### Default Colors
- Default header: `#2d2c2a` (dark)
- Default accent: **Teal** `#34a5a2` — always the default (`DEFAULT_ACCENT_COLOR` in `client/src/styles/accent.ts`); accounts with no saved accent get Teal, and every accent fallback uses it
- Paper background: `#f0ebdf` (light) / `#1a1917` (Midnight)

### Typography
- **Serif** (Playfair Display) — display headings, daily quote
- **Sans** (Lato) — body text
- **UI** (Montserrat) — labels, navigation
- **Brand** (Josefin Sans) — wordmark / logo
- **Mono** (JetBrains Mono) — code, timestamps
